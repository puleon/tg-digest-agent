База данных: где живёт всё, что знает система

Коллектор, ingest-агент, дедупликация, профиль и дайджест работают в разное время и ничего не знают друг о друге. Связывает их одна база данных: каждый шаг читает из неё то, что сделали предыдущие, и записывает своё. В этой главе — как устроена схема, почему выбран Postgres, как код разговаривает с базой и как схема меняется со временем, не ломая данные.

Зачем реляционная база

Реляционная база данных хранит данные в таблицах со строгими столбцами и умеет связывать таблицы между собой: у поста есть канал, у оценки есть пост, у кластера — пост-представитель. Запрос на языке SQL может, например, за один проход найти «все посты юмористических каналов за три месяца, у которых ещё нет обогащения текущей версии» — ровно так ingest выбирает себе работу.

Проект использует PostgreSQL 16. Кроме обычных таблиц, он даёт три вещи, без которых пришлось бы писать много кода:

  • Ограничения (constraints): уникальность пары «канал + номер сообщения», внешние ключи «оценка ссылается на существующий пост». База сама не даст записать нарушение — это надёжнее любой проверки в коде.
  • Транзакции: пачка постов и курсор канала записываются вместе или не записываются вовсе.
  • JSONB — столбец с JSON-документом внутри строки. Метки темы, найденные сущности, исходный HTML поста, план выпуска удобнее хранить как документ, чем раскладывать по десятку таблиц.

Как у нас

Обогащение — отдельная таблица, а не столбцы в posts. Так коллектор и ingest никогда не пишут в одни и те же строки, а обогащение можно целиком пересчитать (новой моделью или новым промптом), не трогая собранные данные. Поле model_version вида qwen3.6-35b-a3b+gemma-4-26b-a4b|classify_post.v1|vlm_describe.v1 говорит, какие модели и промпты сделали запись. Ingest ищет посты, у которых нет записи текущей версии, — смена промпта автоматически ставит корпус в очередь на переразметку.

Как код говорит с базой: SQLAlchemy

Код не пишет SQL руками. Таблицы описаны классами Python в src/tgdigest/db/models.py с помощью SQLAlchemy 2 — самой распространённой библиотеки для работы с базами в Python. Её часть ORM (object-relational mapping) превращает строку таблицы в объект и обратно:

class Post(Base):
    __tablename__ = "posts"
    __table_args__ = (UniqueConstraint("channel_id", "tg_message_id"), ...)

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True)
    channel_id: Mapped[int] = mapped_column(ForeignKey("channels.id", ondelete="CASCADE"))
    posted_at: Mapped[datetime] = mapped_column(DateTime(timezone=True))
    text: Mapped[str] = mapped_column(Text, default="")
    enrichment: Mapped[Enrichment | None] = relationship(back_populates="post")

Аннотации типов (Mapped[int]) одновременно описывают столбец и подсказывают проверщику типов mypy, что лежит в поле. Запросы тоже пишутся на Python: select(Post).where(Post.posted_at >= since) — SQLAlchemy сам переведёт это в SQL для нужной базы.

Асинхронность

Весь проект асинхронный: сервер API одновременно ждёт ответа модели для одного запроса и обслуживает другой. Поэтому и база используется в асинхронном режиме — драйвер asyncpg, движок create_async_engine, сессии AsyncSession. Пока база выполняет запрос, программа не стоит на месте, а занимается другими задачами. Подробнее про асинхронность — в главе 13.

Вставка «или обновить»

Две операции встречаются в проекте постоянно, и обе выражены одной SQL-конструкцией ON CONFLICT:

  • insert_ignore — «вставь, если такого ещё нет» (посты коллектора, глава 4);
  • insert_or_update — «вставь, а если запись с таким ключом есть, обнови перечисленные столбцы» (обогащение: повторный прогон с --force перезаписывает разметку на месте).

Обе функции в src/tgdigest/db/upsert.py выбирают диалект по базе: в Postgres и в тестовой SQLite синтаксис одинаковый, но строится разными модулями SQLAlchemy.

Миграции: как схема меняется со временем

Схема не застывает: за 18 дней добавились кэш сущностей, подписи дедупликации, статистика профиля, трейс выпуска. Менять таблицы руками на живой базе опасно — легко забыть изменение на одной из машин. Для этого есть миграции: каждое изменение схемы — маленький скрипт с функциями upgrade() и downgrade(), пронумерованный и привязанный к предыдущему.

# src/tgdigest/db/alembic/versions/0005_digest_trace.py
revision = "0005"
down_revision = "0004"

def upgrade():
    op.add_column("digests", sa.Column("trace_id", sa.String(64), nullable=True))

def downgrade():
    op.drop_column("digests", "trace_id")

Инструмент Alembic хранит в базе номер последней применённой миграции (таблица alembic_version) и по команде make migrate применяет недостающие по порядку. В проекте пять миграций: начальная схема, кэш сущностей, подписи дедупликации, статистика профиля и трейс выпуска.

В CI (глава 16) отдельная задача поднимает чистый Postgres, применяет все миграции и запускает alembic check — сравнение схемы, получившейся из миграций, с классами в models.py. Если кто-то поменял класс и забыл миграцию, проверка падает.

Ловушка

Миграция в репозитории — ещё не миграция в базе. Миграцию 0005 написали и проверили в CI, но на сервере не применили. Через несколько дней первый настоящий выпуск дайджеста упал с column "trace_id" of relation "digests" does not exist. Урок: после синхронизации кода на сервер — alembic upgrade head, и alembic current перед долгим прогоном.

Ловушка

Другая миграция (0004) объявила столбец как обычный JSON, а класс в коде — как JSONB в Postgres. Локально тесты на SQLite этого не заметили, а alembic check в CI — заметил. Именно для таких расхождений проверка и существует.

Время — только в UTC

Все даты хранятся с часовым поясом (DateTime(timezone=True)) и в UTC; контейнер Postgres запущен с TZ=UTC. Telegram отдаёт время с поясом, сервер живёт в московском, ноутбук — где окажется. Хранить единое время и переводить только при показе — единственный способ не получить «пост из будущего» на границе суток. Фильтр «за неделю» в поиске тоже считается в UTC.

Тестовая база

Тестам не нужен Postgres: юнит-тесты поднимают SQLite — базу в одном файле — и создают в ней схему из тех же классов. Так 182 теста идут за секунды и без инфраструктуры. Отдельный набор integration проверяет то, что SQLite не воспроизводит, на настоящем Postgres.

Ловушка

Сначала тесты использовали SQLite «в памяти». Тест параллельного ingest иногда падал в CI: у базы в памяти одно соединение на всех, и откат одной сессии стирал строки, которые только что записала другая. Решение — SQLite в файле во временной папке: у каждой сессии своё соединение, как в настоящей базе. Тест, который падает «иногда», почти всегда ловит реальную разницу между тестовым окружением и боевым.

Ключевая идея

Целостность данных лучше доверять базе, а не коду: уникальность, внешние ключи, транзакции, миграции с проверкой. Код ошибается, перезапускается и падает на середине — база остаётся согласованной.
