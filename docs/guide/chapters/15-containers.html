Контейнеры и внутренняя сеть

Система — это не одна программа, а полтора десятка процессов: база данных, векторная база, языковая модель, пять компонентов Langfuse, сервер API, сборщик. Большинство из них живут в Docker-контейнерах, связанных внутренними сетями. В этой главе — что такое контейнер, как устроены образы и тома, как описывается вся система одним файлом, какие контейнеры работают на сервере, как они находят друг друга и почему снаружи сервера не виден ни один их порт. Все адреса и цифры сняты с сервера командами docker ps, docker network inspect и docker inspect.

Что такое контейнер

{{fig:vm_vs_container|Виртуальная машина эмулирует компьютер целиком, контейнер — нет.}}

Контейнер — это обычный процесс Linux, которому ядро показывает «урезанный мир». Это не виртуальная машина: у него нет своего ядра и виртуального железа, поэтому он запускается за доли секунды и почти не тратит лишней памяти. Иллюзию отдельного компьютера создают два механизма ядра:

  • Пространства имён (namespaces). У процесса своё дерево процессов (соседей он не видит), своя файловая система, свой сетевой стек — интерфейсы, адреса, маршруты, — своё имя хоста.
  • Контрольные группы (cgroups) — ограничения ресурсов: сколько памяти, процессора, процессов можно занять.
Аналогия

Сервер — многоквартирный дом, ядро Linux — его фундамент и коммуникации. Контейнер — квартира: своя дверь, свои комнаты, свой почтовый ящик, а жилец не видит соседей. Образ — типовой проект квартиры, по которому можно быстро «построить» сколько угодно одинаковых. Docker-сеть — внутренняя телефонная линия между определёнными квартирами, а у некоторых линий нет выхода в город.

Образы, слои и тома

Образ (image) — шаблон файловой системы контейнера: операционная система, программа, её зависимости. Он собран из слоёв, доступных только для чтения: базовый Debian, потом пакеты Postgres, потом скрипты запуска. Одинаковые слои у разных образов хранятся один раз. Образы скачиваются из реестров — Docker Hub, GitHub Container Registry (ghcr.io), Quay — и указываются с точной версией: postgres:16, qdrant/qdrant:v1.19.1. Без версии завтрашний запуск может скачать другую программу.

Контейнер — запущенный из образа процесс с тонким слоем записи поверх. Удалили контейнер — слой записи пропал, образ остался. Поэтому данные, которые должны пережить контейнер, хранятся в томах (volumes) — каталогах, которыми управляет Docker и которые подключаются внутрь контейнера.

{{fig:image_layers|Слои образа, слой записи и том.}}

Второй способ подключить данные — bind mount: папка хоста, видимая внутри контейнера. Так llama-server видит файлы моделей (~/models → /models, только для чтения), а Postgres при первом старте получает скрипт, создающий вторую базу для Langfuse.

Docker Compose: система одним файлом

Запускать десяток контейнеров командами вручную — верный способ ошибиться. Docker Compose описывает всю систему в одном YAML-файле: какие сервисы, из каких образов, с какими переменными, томами, портами и зависимостями. Команда docker compose up приводит реальность в соответствие с файлом. Фрагмент docker-compose.yml проекта:

name: tgdigest
services:
  postgres:
    image: postgres:16
    restart: unless-stopped                   # поднимется сам после сбоя и перезагрузки
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set in .env}   # нет в .env — compose откажется стартовать
      TZ: UTC
    ports:
      - "127.0.0.1:5432:5432"               # только на loopback хоста
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tgd -d tgd"]
      interval: 3s

  langfuse-web:
    image: docker.langfuse.com/langfuse/langfuse:4.38.0
    depends_on:
      postgres:   { condition: service_healthy }   # ждать не запуска, а готовности
      clickhouse: { condition: service_healthy }
    environment:
      <<: *langfuse-env                       # общий блок переменных (YAML-якорь)
  • Секреты не лежат в файле: ${POSTGRES_PASSWORD:?…} берётся из .env, который никогда не попадает в git.
  • Якорь YAML x-langfuse-env: &langfuse-env описывает почти три десятка переменных Langfuse один раз, а веб-сервис и обработчик подключают его ссылкой *langfuse-env.
  • Политика перезапуска unless-stopped: контейнер поднимется сам после падения и после перезагрузки сервера, если его не остановили вручную.

Запуск по порядку: проверки здоровья

Langfuse бессмысленно запускать, пока не готовы его базы. «Контейнер запущен» и «сервис готов» — разные вещи: Postgres стартует несколько секунд. Поэтому у каждого сервиса есть healthcheck — команда, которую Docker регулярно выполняет внутри контейнера, — и зависимости с условием service_healthy: ждать не запуска, а успешной проверки.

{{fig:startup_order|Порядок запуска, который выводит Compose.}}

Цель make up поднимает всё и ждёт, пока все сервисы станут healthy; цель make health отдельно проверяет, что Postgres, Qdrant, модель и Langfuse отвечают.

Ловушка

Проверка здоровья веб-сервиса Langfuse по адресу localhost:3000 всегда падала: сервер на Next.js слушает не loopback, а имя хоста контейнера. Рабочая проверка — wget http://$(hostname):3000/api/public/health. А образ MinIO из официального примера Langfuse перестал скачиваться без авторизации (ответ 403) — его заменили образом с Quay. Чужой docker-compose.yml — отправная точка, а не готовое решение.

Почему код проекта — не в контейнере

API и бот работают на хосте как юниты systemd (глава 13), а коллектор, ingest и скрипты оценки запускаются по команде через uv run; все они живут в одном виртуальном окружении Python. Так быстрее разрабатывать (правка кода → make sync → запуск, без пересборки образа), у процессов прямой доступ к папке картинок, а модели эмбеддингов и реранкер на PyTorch получают все ядра процессора без накладных расходов. До сервисов в контейнерах они достают через опубликованные порты на 127.0.0.1. Если проект когда-нибудь переедет на другую машину, API естественно станет ещё одним сервисом в docker-compose.yml.

Сети Docker

Каждый Compose-проект по умолчанию получает свою сеть-мост (bridge): виртуальный коммутатор внутри ядра, к которому подключены контейнеры проекта. У сети своя подсеть, у каждого контейнера — свой адрес в ней, а у моста на хосте — адрес .1, он же шлюз сети.

Как сервис находит сервис: встроенный DNS

Адреса в сети назначаются при запуске и могут меняться, поэтому сервисы обращаются друг к другу по имени. В каждой пользовательской сети Docker работает встроенный DNS-сервер по адресу 127.0.0.11 (у каждого контейнера свой, внутри его сетевого пространства), который знает имена сервисов этой сети. В переменных Langfuse так и написано: CLICKHOUSE_URL=http://clickhouse:8123, REDIS_HOST=redis, …@postgres:5432/langfuse.

{{fig:dns_lookup|Разрешение имени внутри контейнера langfuse-web — проверено командой getent hosts.}}

Важное свойство: сеть — это граница. Для langfuse-web имени llm-server не существует, потому что модель в другой сети. Ровно поэтому модель вынесли в отдельный проект со своей сетью: агенту ассистента нужен доступ к модели, но не к базе tg_digest, ClickHouse и MinIO, а будь модель сервисом этого проекта, ему пришлось бы подключиться к tgdigest_default — и он увидел бы всё.

Публикация портов: только 127.0.0.1

У сервера публичный адрес в домашней сети, и всё, что опубликовано на 0.0.0.0, увидит каждое устройство в ней. Поэтому все порты опубликованы только на 127.0.0.1: к ним могут подключиться процессы самого сервера — и никто больше. Как это работает: запись "127.0.0.1:5432:5432" заставляет Docker запустить на хосте процесс docker-proxy, который слушает 127.0.0.1:5432 и пересылает соединения на 172.18.0.6:5432; для остальных случаев ядро делает то же правилами NAT. На сервере таких прокси девять.

Единственное исключение — модель: она опубликована ещё и на 172.17.0.1:8080, адресе моста docker0. Агенты персонального ассистента работают в контейнерах на этом мосту и обращаются к модели как к host.docker.internal:8080, а это имя внутри контейнера указывает именно на 172.17.0.1. Этот адрес тоже не виден из внешней сети.

Как у нас

У MinIO два адреса для одного и того же хранилища: внутренний http://minio:9000 — для langfuse-web и worker, и http://localhost:9090 — для вашего браузера, когда он скачивает вложения трейса через туннель. Langfuse отдаёт браузеру ссылку на внешний адрес, а сам ходит по внутреннему; оба заданы в переменных …_ENDPOINT и …_INTERNAL_ENDPOINT.

Выход наружу: таблица маршрутов и VPN

Каждый раз, когда программа отправляет пакет, ядро Linux решает, через какой интерфейс его выпустить. Для этого есть таблица маршрутов — список строк «подсеть → интерфейс». Подсеть записывают как адрес и длину префикса: 149.154.160.0/20 — все адреса, у которых совпадают первые 20 бит, то есть 4 096 адресов от 149.154.160.0 до 149.154.175.255. Строка default — это 0.0.0.0/0, префикс нулевой длины, под который подходит любой адрес.

{{fig:route_table|Три адреса и три решения ядра.}}

Если подходят несколько строк, побеждает самая длинная — правило longest prefix match. Адрес t.me (149.154.167.99) подходит и под default, и под /20; /20 конкретнее, поэтому пакет уходит в xray-tg. Адрес Википедии подходит только под default и идёт через обычный сетевой интерфейс enp10s0 к роутеру. Сети Docker из предыдущего раздела — такие же строки: у каждой сети свой мост br-….

TUN-устройство — виртуальный сетевой интерфейс, за которым вместо кабеля стоит программа. Ядро «отправляет» пакет в xray-tg, а процесс xray читает его из устройства, как из файла, и везёт на VPN-узел внутри обычного TLS-соединения с адреса сервера. Адрес самого узла не входит в подсети Telegram, поэтому это соединение идёт через default и петли не возникает. Ответы проходят обратный путь: xray записывает их в устройство, и для программы они выглядят как обычные пакеты от Telegram. Коллектор и бот ничего не знают о VPN — в отличие от SOCKS-прокси, который нужно было прописывать каждой программе отдельно.

Маршруты к подсетям Telegram добавляет юнит systemd xray-telegram, когда устройство появляется, и они исчезают вместе с ним, когда xray остановлен. Список подсетей официальный — Telegram публикует его сам: 9 подсетей IPv4 и 5 IPv6. Юнит принадлежит соседнему проекту, ассистенту: маршрут — общий ресурс хоста, как llama-server, только без своего репозитория, поэтому tg_digest проверяет его в tgdigest health.

Как у нас

Контейнеры выходят в интернет через NAT хоста: Docker ставит правило MASQUERADE, которое подменяет адрес контейнера адресом интерфейса, через который пакет уходит. Решение «через какой интерфейс» принимает та же таблица маршрутов, поэтому VPN-маршрут работает и для контейнеров: из сети tgdigest_default t.me отвечает так же, как с самого хоста. Проверить, куда уйдёт пакет, можно одной командой: ip route get 149.154.167.99 → dev xray-tg.

Ловушка

Подсети Docker — обычные строки этой же таблицы (172.19.0.0/16 dev br-…). Когда при настройке VPN соседнего проекта завели сетевой интерфейс с маленькой подсетью внутри 172.19.0.0/16, ядро стало отправлять часть пакетов к llm-server в VPN — более узкий маршрут всегда побеждает. tg_digest на 18 часов потерял доступ к модели, а проверка конфигурации VPN проходила без ошибок. Прежде чем давать адрес любому интерфейсу на сервере, посмотрите ip route и подсети Docker.

Доступ снаружи: SSH-туннели

Раз порты видны только на самом сервере, как открыть интерфейс Langfuse в браузере ноутбука? Через SSH-туннель: SSH умеет не только давать командную строку, но и переправлять соединения внутри зашифрованного канала.

{{fig:ssh_tunnels|Локальный туннель и запасной обратный.}}
  • Локальный (ssh -L 3000:127.0.0.1:3000 shevek, цель make tunnel): порт 3000 на ноутбуке ведёт на 127.0.0.1:3000 сервера. Так открываются Langfuse, Qdrant, модель и API.
  • Обратный (ssh -N -R 1080 shevek): на сервере появляется SOCKS-прокси, соединения через который выходят в интернет с ноутбука. Так сервер доставал Telegram, пока не было VPN-маршрута (глава 4). Теперь это запасной путь: если маршрут упадёт, достаточно открыть туннель и прописать WEB_PROXY / BOT_PROXY в .env сервера.

В обоих случаях на сервере не открыто ни одного порта наружу, кроме самого SSH.

Ключевая идея

Сеть — это и связь, и граница. Сервисы одного проекта видят друг друга по именам, сервисы разных проектов — только через явно открытую дверь, процессы хоста — только через loopback, а внешний мир — никого. Каждая такая граница — решение «кто кому должен быть виден», а не настройка по умолчанию.
