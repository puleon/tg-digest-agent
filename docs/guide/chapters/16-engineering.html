Инженерная кухня

Агентная система — это в первую очередь программа, и к ней применимы все обычные практики: управление зависимостями, проверка типов, тесты, непрерывная интеграция, секреты вне репозитория. В проекте с моделью к ним добавляются свои: версии промптов, поддельные модели в тестах, журнал экспериментов. В этой главе — как всё это устроено и как выглядит рабочий процесс между ноутбуком и сервером.

Всё приложение — одна команда командной строки tgdigest с подкомандами (collector, ingest, dedup, index, agent, profile, digest, prompts, api, bot, health), построенная на библиотеке Typer. Каждый шаг конвейера можно запустить вручную, по одной теме или с ограничением по дате.

Зависимости: uv

Python-окружение собирает uv — быстрый менеджер пакетов. Зависимости объявлены в pyproject.toml, точные версии всего дерева зафиксированы в uv.lock, и uv sync --frozen на любой машине ставит ровно те же версии. Требуется Python 3.12. Тяжёлые пакеты — PyTorch (только CPU-сборка), FlagEmbedding, scikit-learn — подтягиваются тем же способом.

Качество кода: ruff, mypy, pre-commit

  • ruff — линтер и форматтер: стиль, неиспользуемые импорты, типичные ошибки, правила безопасности (вшитые пароли, небезопасные вызовы подпроцессов), асинхронные ловушки вроде блокирующего чтения файла внутри async-функции.
  • mypy в строгом режиме проверяет типы во всём коде, тестах и скриптах. Для агентной системы это особенно ценно: состояние графа — словарь с десятками полей, и опечатка в имени поля ловится до запуска.
  • pre-commit запускает ruff, проверку YAML, поиск приватных ключей и запрет на коммит .env перед каждым коммитом.

Тесты без модели

Главный вопрос тестирования агентной системы: как проверить код, который вызывает модель, если модель медленная, большая и недетерминированная? Ответ — поддельные зависимости: каждую внешнюю часть заменяет простой заменитель с предсказуемым поведением.

{{fig:test_fakes|Что чем заменяется в тестах.}}

Например, ScriptedLLM в тестах агента отвечает роутеру заданным режимом, предлагает заданные формулировки, считает релевантными посты с заданным словом и по заказу «ломается» на выбранном шаге. Тест проверяет не ум модели, а логику графа: после двух неудачных переформулировок агент идёт в синтез, сломанный роутер даёт режим search, исчерпанный бюджет даёт оговорку.

Что тестируется обязательно (правило спецификации): дедупликация, разбор ответов модели зрения, отказы инструментов, идемпотентность. Всего 182 юнит-теста; они идут меньше минуты и не требуют ни одного сервиса. Интеграционные тесты помечены @pytest.mark.integration и запускаются на настоящем Postgres.

Непрерывная интеграция

{{fig:ci_jobs|Три задачи CI.}}

GitHub Actions на каждый push проверяет стиль, типы и тесты; отдельная задача поднимает Postgres, применяет миграции и сверяет схему с кодом; третья ищет утёкшие секреты во всей истории git (gitleaks). Репозиторий публичный с первого коммита — поэтому секретам в нём не место ни в каком виде.

Конфигурация и секреты

Все настройки — в классе Settings (src/tgdigest/config.py) на pydantic-settings: значения берутся из переменных окружения и файла .env, проверяются по типам, а пароли и токены хранятся в типе SecretStr, который не печатается в логах. .env.example в репозитории перечисляет все переменные с пояснениями, но без значений; настоящий .env есть только на машинах, где система работает.

Между ноутбуком и сервером

{{fig:dev_workflow|Рабочий процесс.}}

Код пишется и проверяется на ноутбуке, а работает на сервере. make sync копирует дерево через rsync, исключая .env, данные, модели и результаты экспериментов (они рождаются на сервере и забираются обратно make pull-results). Долгие задачи — обогащение, оценки — запускаются на сервере скриптами через nohup с записью в лог, часто цепочками: «дождаться окончания судьи → поставить ingest на паузу → прогнать тяжёлую модель → вернуть ingest». Так сервер работает ночью без присмотра, а одна модель делится между задачами по очереди.

Ловушка

Команда pkill -f "eval_chain", переданная по ssh одной строкой, убивала саму ssh-сессию: шаблон совпадал с командной строкой оболочки, которая эту команду и выполняла. Трижды. Правило: команды, убивающие процессы по шаблону, — только из скрипта, скопированного на сервер.

Всё под версией

  • Код — git, Conventional Commits («feat(agent): …», «fix(collector): …»), 1–2 осмысленных коммита на день плана, около ста коммитов.
  • Схема базы — миграции Alembic (глава 5).
  • Промпты — номер версии в имени файла, никаких правок на месте (глава 14).
  • Данные обогащения — model_version в каждой записи: какая модель и какой промпт.
  • Эксперименты — отчёт и сырые результаты в репозитории, прогоны в Langfuse.
  • Решения — PROGRESS.md: что сделано, что измерено, что не получилось, что отклонилось от спецификации и почему.
