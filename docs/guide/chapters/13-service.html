Сервис: API и Telegram-бот

Всё, что описано до сих пор, — библиотека функций и командная строка. Чтобы этим можно было пользоваться с телефона, нужна дверь: HTTP API, который принимает запросы и отдаёт ответы в JSON, и Telegram-бот, который превращает ваши сообщения в запросы к API, а ответы — в сообщения с кнопками. В этой главе — как они устроены и почему бот — лишь тонкий клиент API.

Зачем API, если есть бот

Можно было бы встроить агента прямо в бота. Но тогда бот должен жить там же, где модели, база и индекс, а сервер не может достучаться до Telegram (глава 4). Разделение решает это: API работает на сервере рядом с данными и моделями, бот — где угодно, где есть доступ к Telegram, и ходит в API по HTTP. Бонусы: API можно вызывать из скриптов и тестов, а бот можно заменить на веб-интерфейс, не трогая логику.

Всю логику API получает из одного объекта Services (src/tgdigest/service.py): он при старте открывает подключения к базе, Qdrant, модели, загружает BGE-M3 и реранкер и предоставляет методы ask, digest, feedback, profile. Теми же методами пользуются оценочные скрипты — так эксперимент гоняет ровно тот код, который работает в боте.

FastAPI и асинхронность

FastAPI — веб-фреймворк для Python, в котором обработчик запроса — обычная функция с аннотациями типов, а схемы запросов и ответов — Pydantic-модели. По ним FastAPI сам проверяет входящий JSON, сериализует ответ и строит документацию.

@app.post("/search", response_model=SearchResponse)
async def search(req: SearchRequest) -> SearchResponse:
    state = await svc().ask(req.query, user_id=req.user_id)
    return SearchResponse(answer=state["answer"], citations=..., degraded=..., trace_id=...)

Ключевое слово async здесь главное. Запрос к агенту длится минуты, и почти всё это время процесс API ничего не делает — ждёт ответа от llama-server. В асинхронной программе ожидание (await) отдаёт управление циклу событий, и тот обслуживает другие запросы.

{{fig:async_loop|Четыре запроса к одному процессу API. Ожидание модели не блокирует остальных.}}

Важная оговорка: асинхронность помогает только при ожидании. Вычисления на процессоре — эмбеддинг запроса, реранкер — блокировали бы цикл, поэтому инструмент поиска выполняет их в отдельном потоке через asyncio.to_thread. Сервер запускает uvicorn — ASGI-сервер, который принимает HTTP-соединения и передаёт их приложению. Команда make api, адрес 127.0.0.1:8000; модели загружаются при старте около минуты (блок lifespan), и дальше каждый запрос использует уже загруженные.

Метрики

/metrics отдаёт текст в формате Prometheus — стандарте, который понимают системы мониторинга: счётчики запросов по эндпоинтам и кодам ответа, суммарное время запросов, токены модели, число кругов агента.

Библиотека для этого не понадобилась: формат текстовый и простой, вся реализация — полсотни строк в api/metrics.py.

Бот на aiogram

Бот написан на aiogram 3 — асинхронной библиотеке для Telegram Bot API. Бот — это программа, которая зарегистрирована у Telegram (через @BotFather) и получила токен — пароль, которым подписывается каждый запрос к api.telegram.org.

Получать сообщения можно двумя способами. Вебхук — Telegram сам отправляет каждое сообщение на ваш публичный HTTPS-адрес; для этого нужен адрес, доступный из интернета. Long polling — бот сам спрашивает «есть новое?», и Telegram держит запрос открытым, пока сообщение не появится. У бота проекта нет публичного адреса, поэтому — long polling: dp.start_polling(bot).

{{fig:bot_sequence|Путь одного вопроса.}}

Код бота — набор обработчиков, привязанных к фильтрам: команда /digest, команда /why, любой текст без слэша (это поиск), нажатие кнопки с данными, начинающимися на fb:. Обработчик поиска сначала отвечает «Ищу… на CPU это может занять пару минут» — пользователь должен видеть, что его услышали, — потом вызывает API и заменяет это сообщение ответом.

Кнопки и их данные

Под ответом — инлайн-клавиатура: кнопки, нажатие которых не отправляет текст, а приходит боту как событие с короткой строкой callback_data — не длиннее 64 байт. В неё упаковано всё, что нужно, чтобы обработать нажатие без хранения состояния в боте:

{{fig:keyboard|Кнопки и строки, которые в них зашиты.}}

Нажатие 👍 превращается в POST /feedback с сигналом, постом, контекстом и id трейса. API записывает голос в базу и ставит оценку на трейс того прогона, который нашёл пост, — в Langfuse видно, каким ответам ставили лайки.

Кто может пользоваться

Бот личный. Список разрешённых Telegram-id задаётся в BOT_ALLOWED_USERS; остальным бот молча не отвечает, а в журнал пишет id отвергнутого пользователя — так владелец узнаёт свой id, чтобы вписать его в список.

Ежедневный выпуск

Команда /schedule 9 сохраняет в профиле час (по UTC). Внутри бота работает цикл: раз в минуту он спрашивает API «кому пора» и, если у пользователя ещё нет выпуска за сегодня, собирает и отправляет его. Проверка «уже был сегодня» идёт по сохранённым выпускам, поэтому перезапуск бота не приведёт к двойной отправке.

Где живёт бот

{{fig:bot_placement|Бот и API — два юнита systemd на сервере.}}

Бот работает на сервере, рядом с API, и ходит к нему по 127.0.0.1:8000. В Telegram он выходит напрямую: адреса Telegram сервер отправляет через VPN-маршрут (глава 4), поэтому BOT_PROXY пуст. Так было не всегда: пока Telegram с сервера был недоступен, бот приходилось запускать на ноутбуке, а к API пробрасывать SSH-туннель make tunnel, и ежедневные выпуски зависели бы от открытого ноутбука.

Чтобы бот и API жили сами по себе, их запускает systemd — менеджер служб Linux. Служба описывается коротким файлом-юнитом: какую команду запустить, в каком каталоге, что делать при падении. Юниты лежат в репозитории (deploy/systemd/), make units копирует их в ~/.config/systemd/user/. Это пользовательские юниты: они работают от имени владельца, без root, а настройка Linger позволяет им стартовать при загрузке сервера, даже если никто не вошёл в систему. Юнит бота запускается после юнита API и с условием ExecCondition: пока в .env нет BOT_TOKEN, systemd просто не стартует бота, а не перезапускает его каждые 10 секунд с ошибкой. Токен живёт только в .env сервера и никогда не попадает в репозиторий.

Ловушка

Ответ агента идёт минуты, а HTTP-клиенты по умолчанию ждут секунды. У клиента API в боте таймаут 30 минут, у клиента модели в API — 10 минут. Таймауты нужно выбирать под реальную длительность операции, а не оставлять библиотечные: иначе бот будет сообщать об ошибке, пока агент спокойно дописывает ответ.
