Наблюдаемость: Langfuse

Агент, который ответил за 15 минут, — это вопрос: где ушло время? Ответ, в котором нет ссылки на нужный пост, — тоже вопрос: не нашёл, нашёл и отбросил на оценке или нашёл, но не процитировал? Обычные логи на такие вопросы отвечают плохо. Нужна трассировка: запись каждого шага каждого прогона с входом, выходом, временем и токенами. В проекте её ведёт Langfuse — открытая платформа наблюдаемости для LLM-приложений, развёрнутая на том же сервере.

Логи, трейсы, метрики

Наблюдаемость обычно строят из трёх вещей:

  • Логи — события по одному: «инструмент search_index отработал за 0,2 с». В проекте их пишет structlog, и каждое событие — не строка текста, а набор полей (tool=search_index seconds=0.216), который можно отфильтровать и посчитать.
  • Метрики — числа во времени: сколько запросов, сколько токенов (эндпоинт /metrics, глава 13).
  • Трейсы — дерево событий одной операции: прогон агента и все его шаги вложены друг в друга. Для агента это главное.

Трейс прогона

{{fig:trace_tree|Трейс прогона из главы 2. Каждое наблюдение кликабельно: вход, выход, промпт, модель, токены.}}

Трейс — одна операция целиком: прогон агента или сборка выпуска. Внутри — наблюдения (observations) разных типов: generation — вызов модели (с моделью, токенами входа и выхода), retriever — поиск, tool — вызов инструмента, span — любой другой участок. У трейса есть пользователь, вход и выход; к нему можно привязать оценки (scores).

Как у нас

Граф агента ничего не знает о Langfuse. Он говорит с интерфейсом Tracer (agent/tracing.py), у которого две реализации: LangfuseTracer — когда в .env есть ключи, и NoopTracer, который ничего не делает, — для тестов и машин без Langfuse. Текущий прогон хранится в contextvars — «глобальной переменной в пределах одной асинхронной задачи», поэтому параллельные запросы к API не путают свои трейсы. Любая ошибка трейсинга перехватывается и пишется в лог: наблюдаемость не имеет права уронить то, за чем наблюдает.

Каждый шаг агента пишет те же данные и в своё состояние (state["steps"]), так что прогон можно разобрать и без Langfuse — трейсер лишь отражает то, что агент и так знает о себе.

Оценки на трейсах

Оценка — число (или категория), привязанное к трейсу. Источников два:

  • Голос пользователя. Кнопка 👍 в боте отправляет POST /feedback с id трейса, и API ставит на этот трейс оценку like = 1. Через месяц работы бота можно будет отобрать трейсы с дизлайками и посмотреть, на каком шаге что пошло не так.
  • Автоматическая проверка. Оценочные скрипты ставят на трейсы результаты: релевантность, успех задачи, число шагов, токены.

Датасеты и эксперименты

Датасет в Langfuse — набор тестовых входов с ожидаемыми ответами. Прогон (dataset run) — результат одной версии системы на всём наборе с оценками по каждому элементу. Два прогона одного датасета можно сравнить в интерфейсе построчно — именно так видно, что изменилось между версиями.

ДатасетЭлементовПрогоны

Сами прогоны тяжёлые (часы процессора), поэтому скрипты считают всё локально, а в Langfuse записывают готовые результаты: --langfuse у каждого оценочного скрипта создаёт прогон и ставит оценки по элементам (eval/langfuse_sync.py). Элементы датасетов имеют постоянные id вида research-tasks:r01, поэтому повторная загрузка обновляет, а не дублирует.

Промпты под версией

Все 16 промптов проекта — файлы prompts/<имя>.v<N>.md. Файлы — источник истины: они проверяются в git, а их версии входят в model_version записей обогащения. Промпт никогда не правится на месте: изменение — новая версия (так появился rewrite_query.v2). Команда tgdigest prompts push регистрирует каждый файл в Langfuse с меткой версии, и в интерфейсе видно, каким текстом промпта был сделан тот или иной вызов, и можно сравнить версии.

Как Langfuse устроен внутри

Langfuse — не одна программа, а небольшая распределённая система. На сервере она занимает шесть контейнеров (подробнее о контейнерах — в главе 15):

{{fig:langfuse_arch|Компоненты Langfuse и путь события.}}
  • langfuse-web — веб-интерфейс и API, принимает события от SDK;
  • MinIO — хранилище файлов, совместимое с Amazon S3: сюда сначала складываются сырые события, чтобы ничего не потерять при пиковой нагрузке;
  • Redis — очередь задач «разобрать такое-то событие»;
  • langfuse-worker — фоновый обработчик, который разбирает очередь и пишет в аналитическую базу;
  • ClickHouse — колоночная база для аналитики: трейсы, наблюдения и оценки. Она умеет быстро считать агрегаты по миллионам строк («средние токены по шагу за неделю»). У нас она занимает 3,5 ГБ и больше всех остальных служб;
  • Postgres — тот же экземпляр, что у проекта, но отдельная база langfuse: пользователи, проекты, ключи, промпты, датасеты.

SDK Langfuse построен на OpenTelemetry — открытом стандарте трассировки: наблюдения — это спаны OpenTelemetry, они копятся в памяти процесса и отправляются пачками в фоне. Поэтому трейсинг почти не добавляет времени к шагам агента.

Ловушка

Langfuse 4 работает в режиме «только события», и часть старых API в нём отключена: например, список прогонов датасета или трейсов через публичный API возвращает 404 с пометкой «недоступно в режиме v4». Записывать можно, а смотреть удобнее в интерфейсе: make tunnel и http://localhost:3000.

Ключевая идея

Трассировка нужна не для красоты. Три ошибки внешнего шага агента в главе 9 были найдены только потому, что каждый вызов инструмента оставил запись с видом ошибки. Записывайте то, что делают инструменты, а не только то, что ответила модель.
